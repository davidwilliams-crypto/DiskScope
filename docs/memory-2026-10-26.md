# DiskScope RAM audit — 2026-10-26

Scope: read-only analysis of the existing 0.2.1 source and small recorded resource summaries/samples. No build, scan, application launch, or user file-content inspection. Figures below describe the earlier ordinary-user, headless C: benchmark; they are not a measurement of the new administrator backend or post-scan GUI residency.

## What was measured

From `.superpowers/sdd/diskscope-c-perf/indexed-pairs.summary.json` and the five `indexed-diskscope-*.samples.json` files:

| Metric | DiskScope | WinDirStat |
|---|---:|---:|
| Median sampled private committed peak | 2,379,395,072 B | 930,983,936 B |
| Median OS lifetime peak working set | 1,700,945,920 B | 972,251,136 B |
| Late-run representative working set | 1,089,097,728 B | 862,171,136 B |
| Late-run representative private commit | 1,720,578,048 B | 835,158,016 B |

The late-run values are medians of per-run medians in a window 1.5–0.5 seconds before each final sample. These are useful context, not a matched-phase or steady-state GUI comparison: the programs' reporting/export work differs. Absolute final samples sometimes include teardown and must not be called steady state. The OS peak is a lifetime high-water mark; the 2.38 GB private figure is committed address space, not continuous physical RAM consumption. [Microsoft counter definitions](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex), [working-set definition](https://learn.microsoft.com/en-us/windows/win32/memory/working-set).

## Main cause: retained metadata and arena growth

`src/model.rs:30` defines a uniform Node containing component name, parent/child IDs, sizes, counts, timestamps, file identity and flags. The previously verified Windows layout is **160 bytes per Node** (`docs/validation-0.2.md`). The recorded inventory contains 3,791,572 files + 756,036 folders + root = **4,547,609 Nodes**, requiring **727,617,440 B (694 MiB)** for used Node structs alone. Filename heaps, child-ID allocations, the identity HashMap, unused capacity and allocator overhead are additional. Full paths and file contents are not retained per file.

The arena is a growing `Vec<Node>` (`src/model.rs:56,142`). Four of five sampled runs briefly jump to roughly 2.38 GB private commit around 26.6–26.9 seconds, then release 671.94–672.29 MB in the next 109–125 ms. Example run 2: 2,379,702,272 B at 26,767 ms → 1,707,413,504 B at 26,880 ms. The first run's sampler misses this brief committed peak, while its OS working-set high-water mark is comparable.

This strongly matches moving a 160-byte arena from 4,194,304 to 8,388,608 slots: old buffer **671,088,640 B**, new buffer **1,342,177,280 B**, temporarily both live. At the final node count, that inferred new capacity would leave **614,559,840 B (586 MiB)** unused. This is a source-and-sample inference, **not recorded capacity or an allocator trace**. Rust does not promise a particular growth factor, and Vec does not shrink automatically. [Rust Vec guarantees](https://doc.rust-lang.org/std/vec/struct.Vec.html#guarantees).

Other material costs: child-ID payload is at least 18,190,432 B; the global identity index (`src/model.rs:66,118`) can hold millions of entries. With 157,517 recorded hard-link aliases, at most 3,634,055 distinct file identities would contribute about 102 MB of raw 24-byte keys + 4-byte IDs, before alignment/table slack; missing identities can lower that count. It supports correct hard-link accounting. No allocator breakdown was recorded.

## What the memory buys

Keeping the inventory in memory permits fast navigation, filtering, queries and path reconstruction without rescanning. Simple indexed storage also makes updates inexpensive. Some spare capacity reduces reallocations. Higher RAM itself does not guarantee stability; bounded queues and background work provide responsiveness.

The recent root summary is not the bulk cost: its Top 2048 ID cache is **8 KiB** plus a small header; extension aggregates contain thousands of groups rather than millions of records (`src/view.rs:7,13,27`). Worker/result queues are bounded, and scan history shares the same model via Arc. The benchmark CLI exits before eframe starts, so these RAM figures cannot be attributed to the modern UI or its GPU buffers.

Administrator access may expose additional files and therefore increase inventory RAM. Its potential speed improvement needs its own measurement; elevation alone does not compact the model.

## Recommendation

Keep the useful in-memory inventory. Do not change the arena during the administrator/UI work on inferred savings alone. A small future experiment can record `nodes.len()` and `nodes.capacity()`, then compare a conservative explicit large-arena growth policy or end-of-scan unused-capacity compaction against the current policy. Both preserve Node IDs; either can introduce copying, a transient allocation or completion delay. Adopt only after measuring lower committed/resident memory **and** acceptable scan/ready latency. A chunked arena or split Node layout is a larger subsequent design decision. No memory optimization was implemented in this audit.
