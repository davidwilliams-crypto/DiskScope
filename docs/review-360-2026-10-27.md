# DiskScope 0.3.0 — 360 review, 27 October 2026

Scope: the whole repository at commit `66a5243` (0.3.0 preview): Rust sources, tests, PowerShell/NSIS/Python tooling, docs and README. The review ran on Linux with Rust 1.97; Windows-only code was type-checked and linted for `x86_64-pc-windows-msvc` but not executed. Items marked *verified by type-check only* need a Windows run before release.

Severity: **high** = data loss, wrong result or documented promise broken; **medium** = wrong behaviour in a realistic case or a maintenance trap; **low** = hygiene.

## What was fixed in this pass

| # | Area | Finding | Fix |
|---|---|---|---|
| 1 | engine (medium) | `allocation_complete` was cleared for *every* directory on any Partial/Cancelled scan, so one denied folder blanked allocation for unrelated siblings; the model doc comment promised per-directory tracking. | `Event::Error` now carries the directory id. A directory is complete when its own listing finished without error and all child directories are complete (reverse sweep at finish). Reparse directories count as complete. Regression: `one_failed_directory_leaves_siblings_allocation_known_and_ancestors_unknown`. |
| 2 | engine (medium) | A root listing error after entries were already retained produced `Failed` (CLI exit 1) and "Root could not be read", contradicting README's partial-results promise. | `Failed` only when the root has no retained children; otherwise `Partial` (exit 4). | 3 | platform (medium) | Choosing a junction or link as the scan root produced a silent empty "Scan complete". | The root reparse case is an explicit error; the scan fails with a message naming the cause. README updated. |

## Open items (not changed, or only mitigated)

1. **Recycle Bin can still end in a permanent delete (high).** `IFileOperation` with `FOFX_RECYCLEONDELETE | FOF_WANTNUKEWARNING` and no owner window: when a volume has no Recycle Bin (USB sticks are admitted by `supported_drive_type`), the file exceeds the Bin's size limit, or "Don't move files to the Recycle Bin" is set, the Shell may show its own parentless "permanently delete?" dialog or delete silently. `PreDeleteItem` can only see the *request* flag `TSF_DELETE_RECYCLE_IF_POSSIBLE`, and the sink detects the nuke only in `PostDeleteItem` after the file is gone. The app then reports an error and does not rescan, leaving a stale row. This contradicts README's "permanent deletion requires a checkbox and typing DELETE". Options: query the Bin for the volume (`SHQueryRecycleBinW`) and the `BitBucket` `MaxCapacity`/`NukeOnDelete` values before offering Recycle; set an owner window so the dialog cannot hide; and rescan after any post-delete error. Not implementable blind from Linux.

   **Status: mitigated, not proven (see [Recycle Bin hardening](validation-recycle-bin-hardening.md)).** Mitigated: a pre-Shell refusal on positive evidence (non-fixed drive, `NoRecycleFiles`, `NukeOnDelete`, file size at or over the Bin maximum), a sink veto when Windows clears the recycle bit, an owner window so Windows' own prompt stays in front of DiskScope, a filesystem-checked outcome (`Ok` only with a confirmed Recycle Bin destination), and a rescan plus acknowledgement whenever the file may be gone. Remaining: if Windows prompts for a case the preflight missed and the user answers Yes, the file is deleted after a Windows confirmation that is lighter than typed `DELETE`; DiskScope then reports it but cannot undo it. A Windows run of the validation matrix is still owed.
2. **Undecodable history files are never reclaimed (medium).** Files that fail `decode` are excluded from retention but counted in the budget; five old-schema files can wedge saves until the user clears everything. Deleting them automatically is a policy choice (they are in an app-owned directory under exclusive ownership).
3. **More than 128 `.dsh` files makes history unavailable and Clear fail (low).**
4. **NTFS preview: nonresident `ATTRIBUTE_LIST` is rejected outright (medium)** in `parse_record`, which `$UsnJrnl:$J` commonly has, so the preview may still fall back on system volumes. The parser also allocates per record (`to_vec` in `apply_fixups`, a `HashSet` of attribute keys per record). A full-volume run is still unvalidated.
5. **Rescan after a file action resets navigation (medium UX).** After deleting one file the whole root is rescanned and the user lands on Overview with Back/Forward cleared. Keeping the user's folder would need a stable focus path that survives an in-progress scan.
6. **Admin detection uses `TokenIsElevated` only (low).** With UAC disabled every administrator is permanently in Admin mode with no explanation and no Recycle Bin.
7. **`examples/profile_scan.rs` duplicates the CLI** (arg parsing, poll loop, exit mapping) and its test enshrines `Cancelled → exit 0`.
8. **Tooling hygiene (low):** `Set-StrictMode` is unset in all scripts; the Cargo.toml version regex, assert helpers and relative-path computation are each copy-pasted 2-5 times; `build.ps1`/`dev.ps1` mutate `PATH`/`CARGO_HOME` process-wide; `.gitignore` lines 8-13 are shadowed by line 16; `docs/dependency-notices/README.md` points at an ignored `.superpowers` path; `portable-readme.txt`, `docs/packaging.md` and README URLs still carry the literal version (the release script checks the readme matches `Cargo.toml`, so a bump fails late rather than silently).
9. **UX polish not changed:** the "0 errors" button opens an empty window; the header switches between two layouts when a scan finishes; "Preview · performance validation in progress" is a permanent status-bar label; `Stop`, `Back`, `Forward` and `Pin` appear in the command palette even when unavailable; pinned comparison shows raw byte counts where every other view uses binary units; `stdout` after `AttachConsole` interleaves with the shell prompt because the shell does not wait for a GUI-subsystem process.
10. **Startup cost (low):** every window open decodes and validates up to five 128 MiB snapshots to read catalog summaries, then re-reads both files on Compare.
