# DiskScope 0.3.0 — 360 review, 27 October 2026

Scope: the whole repository at commit `66a5243` (0.3.0 preview): Rust sources, tests, PowerShell/NSIS/Python tooling, docs and README. The review ran on Linux with Rust 1.97; Windows-only code was type-checked and linted for `x86_64-pc-windows-msvc` but not executed. Items marked *verified by type-check only* need a Windows run before release.

Severity: **high** = data loss, wrong result or documented promise broken; **medium** = wrong behaviour in a realistic case or a maintenance trap; **low** = hygiene.

## What was fixed in this pass

## Open items (remaining, or only mitigated)

1. **Recycle Bin can still end in a permanent delete (high).** `IFileOperation` with `FOFX_RECYCLEONDELETE | FOF_WANTNUKEWARNING` and no owner window: when a volume has no Recycle Bin (USB sticks are admitted by `supported_drive_type`), the file exceeds the Bin's size limit, or "Don't move files to the Recycle Bin" is set, the Shell may show its own parentless "permanently delete?" dialog or delete silently. `PreDeleteItem` can only see the *request* flag `TSF_DELETE_RECYCLE_IF_POSSIBLE`, and the sink detects the nuke only in `PostDeleteItem` after the file is gone. The app then reports an error and does not rescan, leaving a stale row. This contradicts README's "permanent deletion requires a checkbox and typing DELETE". Options: query the Bin for the volume (`SHQueryRecycleBinW`) and the `BitBucket` `MaxCapacity`/`NukeOnDelete` values before offering Recycle; set an owner window so the dialog cannot hide; and rescan after any post-delete error. Not implementable blind from Linux.

   **Status: mitigated, not proven (see [Recycle Bin hardening](validation-recycle-bin-hardening.md)).** Mitigated: a pre-Shell refusal on positive evidence (non-fixed drive, `NoRecycleFiles`, `NukeOnDelete`, file size at or over the Bin maximum), a sink veto when Windows clears the recycle bit, an owner window so Windows' own prompt stays in front of DiskScope, a filesystem-checked outcome (`Ok` only with a confirmed Recycle Bin destination), and a rescan plus acknowledgement whenever the file may be gone. Remaining: if Windows prompts for a case the preflight missed and the user answers Yes, the file is deleted after a Windows confirmation that is lighter than typed `DELETE`; DiskScope then reports it but cannot undo it. A Windows run of the validation matrix is still owed.

2. **Recycle on removable drives with the `RecycleBinDrives` policy (low).** Windows then keeps a Recycle Bin on USB flash drives, but DiskScope refuses Recycle on any drive that is not fixed, so those users must use Delete permanently. Not changed on purpose: the value's bit layout is community-sourced, and guessing it wrong would let Recycle run on a drive with no Bin, which is the original bug.
3. **NTFS preview coverage (medium).** A user file or folder with a nonresident `ATTRIBUTE_LIST` (heavily fragmented files, many alternate streams) still sends the whole volume back to the normal scanner, with a specific reason. Reading list clusters from the volume was judged not safely testable here. The decoder also derives the update-sequence array length from the volume's sector size while NTFS uses a 512-byte stride; this is unconfirmed and would only matter on a 4Kn volume, where the preview would fall back. A successful full-volume parity run has still never been performed.
4. **Navigation state after a file action (low).** Back/Forward, pins and expanded folders still start empty after the rescan because they hold node ids that the new scan reassigns. Manual Scan/Rescan from the header still resets navigation.
5. **History startup still reads every retained snapshot once (low)** to verify its checksum: memory is constant but I/O is up to 640 MiB. Compare still decodes two whole snapshots. Unreadable files stay counted in the write budget until Clear.
6. **Tooling hygiene that needs PowerShell to verify (low).** Not changed because no PowerShell was available and a blind semantic change risks breaking the release scripts: `Set-StrictMode` in the ten scripts; the copy-pasted version regex (`release-tools.ps1`, `package-tools.ps1`), `Assert-True`/`Assert-Rejected`/`Assert-Equal`, fixture-cleanup guards and relative-path computation; and the literal version in `portable-readme.txt`, `docs/packaging.md` and the README download URLs. The seven new checks in `scripts/test-release.ps1` have not been executed.
7. **`stdout` after `AttachConsole` interleaves with the shell prompt** because the shell does not wait for a GUI-subsystem process. Not fixable in this binary.
8. **Header at the minimum window width (low).** The totals line can still wrap at 900 px with a very large scan, so the header height is constant only at normal widths.
9. **Windows execution is owed for every Windows-only change in this pass.** See [Open-item fixes: what to run on Windows](validation-open-items-2026-10-27.md).

When several git worktrees build into one `CARGO_TARGET_DIR`, cargo's artifact hashes do not include the worktree path, so one worktree can run another's compiled test binaries. The open-item streams hit this; the numbers above come from a clean rebuild of the merged tree (`cargo clean -p diskscope` for both targets first). Use a per-worktree target directory, or clean the project crate, before gating concurrent worktrees.

Independent read-only reviews covered four slices (scanner/NTFS/model, history/file actions/admin, GUI/view, tooling/docs); every finding above was re-verified against the source before being acted on. Two reviewer claims were rejected on verification: the `Win32_System_Registry` feature is required (the Windows cross-check fails without it), and the history lock has no stale-lock failure mode because ownership is an OS handle.
